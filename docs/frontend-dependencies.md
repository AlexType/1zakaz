# Фронтенд: зависимости и правила использования

Статус: выбранный технический набор. Конкретный дизайн, поля и сценарии остаются предметом продуктового проектирования. Пакеты установлены в `apps/web`; интеграции, которым нужен ещё не созданный backend, подключаются при реализации соответствующего сценария.

## Основа интерфейса

| Пакет                                       | Назначение и правило                                                                                                                                                                                                                                                                            |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@mantine/core`, `@mantine/hooks`           | Общие компоненты, поля, диалоги и хуки. Использовать готовые элементы для админки; для публичных страниц применять их там, где это оправдано дизайном и размером клиентского JavaScript. Не писать собственные аналоги базовых контролов.                                                       |
| `@mantine/notifications`, `@mantine/modals` | Уведомления и подтверждения действий в админке. Сообщение об успехе не подменяет серверную проверку результата; необратимые операции требуют понятного подтверждения.                                                                                                                           |
| `@mantine/spotlight`                        | Глобальный поиск и переходы по панели через `⌘ K` / `Ctrl K`. Компонент отображает результаты, переданные предметными разделами; он не хранит общий клиентский индекс и после появления API не заменяет серверный поиск.                                                                    |
| `@tabler/icons-react`                       | Иконки для компонентов Mantine. Импортировать конкретные иконки, не весь набор.                                                                                                                                                                                                                 |
| `@fontsource-variable/inter`                | Локально поставляемый шрифт интерфейса с кириллицей. Использовать одно семейство для сайта и админки; браузер загружает подходящие подмножества WOFF2 с нашего домена, без запроса к внешнему сервису шрифтов.                                                                                  |
| `@mantine/form`, `zod`                      | Состояние форм и схемы проверки ввода. Для больших административных форм использовать `uncontrolled` mode и `schemaResolver` из Mantine. Правила доступа, расчёта и публикации дополнительно проверяет backend. Не добавлять параллельно React Hook Form и вторые схемы проверки тех же полей.  |
| `@mantine/dates`, `dayjs`                   | Выбор дат и времени в формах. Локаль `ru` и первый день недели — понедельник — настроены для `/admin`. Для простого отображения дат и чисел использовать `Intl`, а не добавлять вторую библиотеку дат. Даты без времени хранить как `YYYY-MM-DD`, моменты времени — с явным часовым поясом/UTC. |
| `react-easy-crop`                           | Кадрирование аватара сотрудника: перемещение и масштабирование изображения, квадратный результат для круглого превью. Библиотека выдаёт координаты; экспорт в WebP/PNG выполняет браузерный Canvas в `features/staff-profile/lib`. Исходный файл нужен для повторного кадрирования.             |

Корневой `app/layout.tsx` подключает Inter, стили `@mantine/core`, `ColorSchemeScript` и `MantineAppProvider` из `src/_app/mantine`; Storybook использует тот же шрифт и провайдер. Провайдер не превращает все вложенные серверные компоненты Next.js в клиентские. Не добавлять `use client` на всю страницу ради одного интерактивного элемента. `app/admin/layout.tsx` подключает стили дат, уведомлений, редактора и `mantine-datatable`, а также `AdminProviders` из `src/_app/admin` с `DatesProvider`, `ModalsProvider`, `Notifications` и `QueryClientProvider`; их клиентский код не нужен публичным маршрутам. Storybook использует тот же `AdminProviders` и отдельно подключает стили таблицы, редактора, фотогалереи и уведомлений. Красная палитра и шрифт задаются общей темой, локальные переопределения добавляются только при необходимости конкретного компонента.

Результаты действий и ошибки запросов показываем через `showActionSuccess` и `showActionError` из `shared/lib`: уведомления Mantine появляются справа снизу и закрываются автоматически. Ошибки проверки полей остаются рядом с формой; сообщение, содержащее ссылку или другое действие, остаётся на экране, пока пользователь с ним работает. Не дублировать один результат одновременно уведомлением и встроенным `Alert`.

Общий макет панели сотрудников в `src/widgets/admin-shell` построен на Mantine `AppShell`, `NavLink`, `Menu` и `@mantine/spotlight`. Полноширинная шапка хранит логотип постоянного размера, глобальный поиск по разделам и рабочим сущностям с сочетанием `⌘ K` / `Ctrl K` и компактные глобальные действия; название текущего раздела выводит только страница. На десктопе навигация переключается между полной и компактной панелью с подсказками к иконкам; переключатель закреплён на её правой границе и доступен в обоих состояниях. На телефоне навигация открывается как меню. Профиль и выход находятся в нижней части навигации. Оболочка принимает доступные результаты поиска, обработчики переходов и выхода, но не загружает данные, не хранит сессию и не определяет права сама. Результат поиска должен вести к сущности или разделу, а после появления API сами данные будут приходить из предметных query, а не храниться в оболочке. Интерактивная сборка существующих разделов живёт отдельно в демонстрационном компоненте Storybook на уровне `src/_app/admin/AdminWorkspaceDemo`; она не подключает моковые данные к действующему маршруту `/admin`. Дерево Storybook разделяет «Авторизацию» и «Панель управления». В панели путь истории всегда строится как «Панель управления / Раздел / Экран»: «Автомобили», «Статьи» и «Сотрудники» содержат «Список», формы находятся в «Редакторе» или «Приглашении», профиль — в «Профиль / Настройки», общая оболочка — в «Общее / Навигация». Для списков используем одинаковые названия историй: «Основной вид», «Пустой список», «Загрузка», «Ошибка загрузки». Истории создания и изменения живут в «Редакторе». Не соединять список и редактор в одной группе Storybook; интерактивный переход из списка можно показывать отдельной историей списка.

## Наш API и серверное состояние

| Пакет                                          | Назначение и правило                                                                                                                                                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `openapi-typescript` (dev)                     | Генерация TypeScript-типов из OpenAPI-контракта ASP.NET Core API. Типы не редактировать вручную. После появления backend добавить воспроизводимую команду генерации и проверку актуальности в CI.                                          |
| `openapi-fetch`                                | Типизированные HTTP-запросы на основе сгенерированного контракта. Для серверных запросов в Next.js создавать клиент с учётом конкретного запроса и настроек кэширования; не держать пользовательские cookies в общем модульном экземпляре. |
| `@tanstack/react-query`, `openapi-react-query` | Загрузка, кэш и обновление данных в интерактивной админке. `openapi-react-query` связывает Query с типизированным `openapi-fetch`. После изменения записи обновлять соответствующие запросы, а не вести второй самодельный кэш.            |

Публичные SEO-страницы получают данные преимущественно в серверных компонентах Next.js. Настройки `fetch`/revalidate выбираются по природе данных: опубликованная статья и личная заявка требуют разных правил. Браузер и API админки работают на одном origin с cookie-сессией; авторизацию, CSRF-защиту и права обеспечивает .NET API. Для курсов и калькуляторов браузер обращается только к нашему API. До появления реального OpenAPI-контракта нет смысла создавать заглушки с типами «от руки».

## Размещение в FSD

- `app/` содержит маршруты, метаданные и подключение провайдеров. `src/_app/mantine/` и `src/_app/admin/` содержат конфигурацию провайдеров по назначению, без бизнес-логики.
- Общий HTTP-клиент и сгенерированные OpenAPI-типы размещаются в `src/shared/api/`. API-вызовы и query options конкретного предмета — в `entities/<область>/api` либо в `features/<сценарий>/api`, если запрос относится только к действию. Не создавать универсальный файл со всеми endpoints сайта.
- Переиспользуемые композиции Mantine без бизнес-смысла — в `src/shared/ui/`; карточка автомобиля и его таблица принадлежат своей области. Не оборачивать каждый компонент Mantine без причины.
- Таблицы автомобилей, сотрудников и статей используют общие элементы `GridColumnFilter`, `GridTableToolbar`, `GridViewOptions`, `GridPersonCell`, `GridPhotoCell` и `GridErrorState` из `shared/ui`. Кликабельные фото в `GridPhotoCell` показывают лупу при наведении и фокусе, а на сенсорных экранах — постоянную компактную подсказку; действие открывает полноразмерную галерею. Фильтры размещены в заголовках колонок, дата и время выводятся через `formatCompactDateTime`, а настройка плотности и видимости колонок сохраняется отдельно для каждого раздела. На моках фильтрация, сортировка и пагинация выполняются в браузере; после подключения API они должны выполняться на сервере при том же интерфейсе таблиц.
- Редактор статьи, загрузка/сортировка медиа, формы публикации и авторизация сотрудников — сценарии в `features/`, даже если сейчас у сценария единственный маршрут. `_pages/` собирает страницу из публичных API фич и виджетов; не переносить туда их формы, состояния и модели. Компоненты размещать в собственных папках `ui/ComponentName/` с `index.ts` и `ComponentName.tsx`; опциональные стили, тесты и истории — рядом с компонентом. Хуки и утилиты размещать в `lib/` и называть файлы в kebab-case; их тесты — в `lib/test/`, истории — в `lib/stories/`.
- Расчёт денег и бизнес-правила находятся в .NET API. Фронтенд форматирует ответ через `Intl.NumberFormat` и показывает источник и время данных; отдельная библиотека финансовой арифметики на клиенте сейчас не нужна.

Версии зафиксированы в `apps/web/package-lock.json`. Перед добавлением новых библиотек проверять, не решает ли задачу уже установленный Mantine, Next.js или браузерная платформа.

В редакторе автомобиля год выбирается из диапазона 1980 — следующий календарный год, цвет выбирается по ID справочника `{ id, name, hex }`, а страна сопровождается флагом. Числовые поля хранят строку из цифр и показывают разряды пробелами. Описание автомобиля пока хранится как HTML Tiptap в моковой модели; API обязан проверять допустимые элементы и атрибуты перед сохранением и выдачей. Для статей решение о структурированном JSON остаётся в силе. Фото сортируются через актуальный sortable API `@dnd-kit/react` с доступной клавиатурой ручкой; исходные файлы передаются обработчику сохранения, формат и размер показываются по метаданным `File`. Для реальной загрузки и постоянных URL понадобится серверный контракт S3. Общие превью с `contain` поверх размытого фона, просмотр с увеличением и числовые поля находятся в `shared/ui`.

При ручном `form.setFieldValue` в uncontrolled-форме Mantine не ставить на вводимый компонент `key={form.key(...)}`: ключ меняется после каждого изменения и пересоздаёт DOM-элемент, теряя фокус. Для числовых полей использовать `defaultValue` и `setFieldValue(..., { forceUpdate: false })`; повторное обновление полей с сервера требует отдельной явной синхронизации или перемонтирования всей формы после получения новой записи.
