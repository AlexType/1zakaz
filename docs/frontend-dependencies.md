# Фронтенд: зависимости и правила использования

Статус: выбранный технический набор. Конкретный дизайн, поля и сценарии остаются предметом продуктового проектирования. Пакеты установлены в `apps/web`; интеграции, которым нужен ещё не созданный backend, подключаются при реализации соответствующего сценария.

## Основа интерфейса

| Пакет | Назначение и правило |
| --- | --- |
| `@mantine/core`, `@mantine/hooks` | Общие компоненты, таблица, поля, диалоги и хуки. Использовать готовые элементы для админки; для публичных страниц применять их там, где это оправдано дизайном и размером клиентского JavaScript. Не писать собственные аналоги базовых контролов. |
| `@mantine/notifications`, `@mantine/modals` | Уведомления и подтверждения действий в админке. Сообщение об успехе не подменяет серверную проверку результата; необратимые операции требуют понятного подтверждения. |
| `@tabler/icons-react` | Иконки для компонентов Mantine. Импортировать конкретные иконки, не весь набор. |
| `@fontsource-variable/inter` | Локально поставляемый шрифт интерфейса с кириллицей. Использовать одно семейство для сайта и админки; браузер загружает подходящие подмножества WOFF2 с нашего домена, без запроса к внешнему сервису шрифтов. |
| `@mantine/form`, `zod` | Состояние форм и схемы проверки ввода. Для больших административных форм использовать `uncontrolled` mode и `schemaResolver` из Mantine. Правила доступа, расчёта и публикации дополнительно проверяет backend. Не добавлять параллельно React Hook Form и вторые схемы проверки тех же полей. |
| `@mantine/dates`, `dayjs` | Выбор дат и времени в формах. Локаль `ru` и первый день недели — понедельник — настроены для `/admin`. Для простого отображения дат и чисел использовать `Intl`, а не добавлять вторую библиотеку дат. Даты без времени хранить как `YYYY-MM-DD`, моменты времени — с явным часовым поясом/UTC. |

Корневой `app/layout.tsx` подключает Inter, стили `@mantine/core`, `ColorSchemeScript` и `MantineAppProvider` из `src/_app/mantine`; Storybook использует тот же шрифт и провайдер. Провайдер не превращает все вложенные серверные компоненты Next.js в клиентские. Не добавлять `use client` на всю страницу ради одного интерактивного элемента. `app/admin/layout.tsx` подключает стили дат и уведомлений, а также `AdminProviders` из `src/_app/admin` с `DatesProvider`, `ModalsProvider`, `Notifications` и `QueryClientProvider`; их клиентский код не нужен публичным маршрутам. Красная палитра и шрифт задаются общей темой, локальные переопределения добавляются только при необходимости конкретного компонента.

## Наш API и серверное состояние

| Пакет | Назначение и правило |
| --- | --- |
| `openapi-typescript` (dev) | Генерация TypeScript-типов из OpenAPI-контракта ASP.NET Core API. Типы не редактировать вручную. После появления backend добавить воспроизводимую команду генерации и проверку актуальности в CI. |
| `openapi-fetch` | Типизированные HTTP-запросы на основе сгенерированного контракта. Для серверных запросов в Next.js создавать клиент с учётом конкретного запроса и настроек кэширования; не держать пользовательские cookies в общем модульном экземпляре. |
| `@tanstack/react-query`, `openapi-react-query` | Загрузка, кэш и обновление данных в интерактивной админке. `openapi-react-query` связывает Query с типизированным `openapi-fetch`. После изменения записи обновлять соответствующие запросы, а не вести второй самодельный кэш. |

Публичные SEO-страницы получают данные преимущественно в серверных компонентах Next.js. Настройки `fetch`/revalidate выбираются по природе данных: опубликованная статья и личная заявка требуют разных правил. Браузер и API админки работают на одном origin с cookie-сессией; авторизацию, CSRF-защиту и права обеспечивает .NET API. Для курсов и калькуляторов браузер обращается только к нашему API. До появления реального OpenAPI-контракта нет смысла создавать заглушки с типами «от руки».

## Контент, фотографии и рабочие списки

| Пакет | Назначение и правило |
| --- | --- |
| `@mantine/tiptap`, `@tiptap/react`, `@tiptap/pm`, `@tiptap/starter-kit`, `@tiptap/extension-link` | Редактор **тела статьи**: заголовки, списки, ссылки, форматирование. Хранить структурированный Tiptap JSON; набор разрешённых узлов зафиксировать в редакторе, API и серверном рендерере. Публикацию и предпросмотр делать из одной модели. Не разрешать произвольный HTML без проверки. Остальные поля статьи (обложка, рубрика, SEO, статус) остаются обычной формой. |
| `@mantine/carousel`, `embla-carousel`, `embla-carousel-react` | Карусели фотографий и подборок. Использовать Mantine Carousel; Embla — её обязательный движок, а не второй независимый слайдер. Стили `@mantine/carousel/styles.css` подключать там, где появится первая карусель. Автопрокрутку не включать по умолчанию. |
| `@mantine/lightbox` | Полноэкранный просмотр фотографий автомобиля/кейса с клавиатурной навигацией и увеличением. Стили `@mantine/lightbox/styles.css` подключать вместе с первой галереей. |
| `@uppy/core`, `@uppy/react`, `@uppy/aws-s3`, `@uppy/dashboard` | Пакетная загрузка фото с прогрессом и повторной попыткой. После появления медиа-API .NET выдаёт подписанные операции для S3 Timeweb; секреты S3 не попадают в браузер. Backend подтверждает завершение и привязывает файл к записи. Не дублировать загрузчик через `@mantine/dropzone`. |
| `@tanstack/react-table` | Состояние сортировки, фильтров, выделения и колонок для рабочих списков. Визуально таблицу рендерят компоненты `@mantine/core` (`Table` и другие); TanStack Table не является вторым UI-китом. Для больших каталогов фильтрацию и пагинацию выполняет API. |
| `@dnd-kit/react`, `@dnd-kit/helpers` | Перетаскивание и сортировка фотографий/контентных элементов в админке. Использовать актуальный React API dnd-kit; старые пакеты `@dnd-kit/core` и `@dnd-kit/sortable` не устанавливать. Кнопки перемещения должны оставаться доступны с клавиатуры. |

Стили `@mantine/tiptap/styles.css` уже подключены в административном layout. Стили Uppy Dashboard добавляются на экран загрузки при его реализации; если готовый Dashboard не впишется в дизайн, Uppy сохраняем как движок, а UI строим на его React hooks. Изображения на публичном сайте выводим через `next/image` с настроенным доменом S3/CDN после выбора адреса бакета; библиотека для обычного вывода изображений не нужна.

## Размещение в FSD

- `app/` содержит маршруты, метаданные и подключение провайдеров. `src/_app/mantine/` и `src/_app/admin/` содержат конфигурацию провайдеров по назначению, без бизнес-логики.
- Общий HTTP-клиент и сгенерированные OpenAPI-типы размещаются в `src/shared/api/`. API-вызовы и query options конкретного предмета — в `entities/<область>/api` либо в `features/<сценарий>/api`, если запрос относится только к действию. Не создавать универсальный файл со всеми endpoints сайта.
- Переиспользуемые композиции Mantine без бизнес-смысла — в `src/shared/ui/`; карточка автомобиля и его таблица принадлежат своей области. Не оборачивать каждый компонент Mantine без причины.
- Редактор статьи, загрузка/сортировка медиа, формы публикации и авторизация сотрудников — сценарии в `features/`, даже если сейчас у сценария единственный маршрут. `_pages/` собирает страницу из публичных API фич и виджетов; не переносить туда их формы, состояния и модели. Компоненты размещать в собственных папках `ui/ComponentName/` с `index.ts` и `ComponentName.tsx`; опциональные стили, тесты и истории — рядом с компонентом. Хуки и утилиты размещать в `lib/` и называть файлы в kebab-case; их тесты — в `lib/test/`, истории — в `lib/stories/`.
- Расчёт денег и бизнес-правила находятся в .NET API. Фронтенд форматирует ответ через `Intl.NumberFormat` и показывает источник и время данных; отдельная библиотека финансовой арифметики на клиенте сейчас не нужна.

Версии зафиксированы в `apps/web/package-lock.json`. Перед добавлением новых библиотек проверять, не решает ли задачу уже установленный Mantine, Next.js или браузерная платформа.
