# Предлагаемая архитектура

Статус: рабочее предложение, не приказ создавать инфраструктуру.

## Компоненты

- Один монорепозиторий для Next.js/React/TypeScript, ASP.NET Core API, общей документации и инфраструктурных конфигураций. Начальная конфигурация фронтенда уже находится в `apps/web`; backend и развёртывание добавляются отдельными задачами.
- Next.js App Router обслуживает публичные страницы с серверным рендерингом и интерфейс сотрудников. Интерфейс сотрудников — маршрут `app/admin`, публичный URL `/admin` на домене сайта. Интерактивный код загружается там, где нужен. Next.js не становится вторым источником бизнес-правил и не обращается напрямую к PostgreSQL.
- Один ASP.NET Core API как модульное приложение. Предполагаемые области: контент и SEO, каталог конкретных автомобилей/кейсов, расчёты, заявки, медиа, сотрудники/права и настройки. Марка и модель — данные автомобиля для поиска и группировки; отдельный модуль публичных страниц моделей сейчас не утверждён. Границы уточняются по рабочим сценариям. Контракт API описывается в OpenAPI; клиентские типы синхронизируются с ним.
- PostgreSQL — структурированные записи, связи, состояния, журнал изменений и параметры расчётов. S3 Timeweb — оригиналы и производные изображений. В БД хранятся ссылки и метаданные файлов.
- Авторизация сотрудников, разграничение ролей, проверка загрузок, резервные копии и восстановление входят в проект, а не добавляются после запуска. Предлагаемая схема входа и восстановления — в [отдельном документе](admin-auth.md).

## Данные для калькуляторов

Для каждого параметра администратор выбирает режим `ручной` либо `автоматический`, если для него есть проверенный источник. Автоматическое значение показывает источник и время обновления; перед сохранением ручного переопределения сотрудник видит итог расчёта. Фоновый worker получает и проверяет справочные данные, сохраняет версии в PostgreSQL; запрос калькулятора выполняется через API по выбранной опубликованной версии. При недоступности источника нельзя незаметно переходить на выдуманные константы. Для каждой страны могут быть разные правила; обещать точную цену без согласованной методики нельзя. Исследование конкретных источников и ограничений — в [отдельном документе](data-sources.md).

## Окружения и поставка

- Локально: Next.js запускается непосредственно на Mac; API, PostgreSQL и S3-совместимый сервис — через Docker Compose. Для локальной разработки используются вымышленные персональные данные.
- Тестовое окружение: отдельный сервер, база и бакет в российской локации. Уведомления и интеграции настраиваются так, чтобы тестовые заявки не уходили реальным клиентам.
- Продакшен: отдельный от старого Bitrix сервер под Next.js и API в Docker Compose, управляемый PostgreSQL Timeweb и S3 Timeweb. База без публичного доступа, если приложение подключено через приватную сеть. Размещение всех компонентов, резервных копий и логов с персональными данными в РФ проверяется отдельно.
- GitHub Actions: проверки PR; сборка версии; автоматическая выкладка в тестовое окружение после слияния; продакшен — из зафиксированной версии с отдельным запуском и проверкой. Миграции БД, резервная копия и возможность отката входят в процедуру выпуска. Детальный механизм будет выбран после создания окружений.

GitHub может хранить исходный код и выполнять сборку, но персональные данные клиентов и производственные секреты не должны попадать в репозиторий, артефакты или логи CI. Соответствие 152-ФЗ требует анализа всей обработки заявок, включая почту, CRM, аналитику и внешние API, а не только выбора российского хостинга.

## Правила поддерживаемости

Для фронтенда используем [рекомендации FSD для Next.js](https://feature-sliced.design/docs/guides/tech/with-nextjs): маршруты Next.js лежат в `app`, слои FSD — в `src` как `_app`, `_pages`, `widgets`, `features`, `entities`, `shared`. Подчёркивание у `_app` и `_pages` нужно потому, что Next.js резервирует имена `app` и `pages`. Не создаём срез ради одного файла; не выносим весь код страницы в виджеты искусственно. На backend — разделение по предметным областям и короткие сценарии внутри них, с проверками критичных правил расчёта и публикации. Архитектурные решения фиксируются вместе с причиной и последствиями.

Выбранные фронтенд-зависимости, их границы и правила размещения в FSD описаны в [отдельном документе](frontend-dependencies.md). Наличие пакета не означает, что его нужно импортировать на каждой странице.
