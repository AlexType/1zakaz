## Как обновлять данные

1. Отдельный .NET worker по расписанию получает **справочные данные**, прежде всего курсы ЦБ. Следующее обращение к калькулятору **не ждёт** обновления этих справочников. Для курса ЦБ фиксируются дата действия и время получения; выходные не считаются сбоем только потому, что нового выпуска курса нет.
2. Адаптер источника приводит ответ к нашим единицам измерения и проверяет формат, полноту, диапазоны, резкие отклонения и дубль версии. Ошибка не меняет опубликованные значения. Система сообщает администратору об устаревании.
3. В PostgreSQL сохраняются источник, исходная дата, время загрузки, нормализованное значение, версия и статус. Автопубликация допустима для проверенных ежедневных курсов; юридические ставки и собственные тарифы проходят подтверждение человеком.
4. API считает стоимость по опубликованному набору правил и данных. В результате сохраняются входные параметры, идентификаторы версий и подробная разбивка, чтобы воспроизвести расчёт позже. Слишком старое значение отображается как устаревшее либо блокирует расчёт — пределы свежести согласуются по каждому источнику.
5. Интерфейс администратора показывает режим поля: `автоматически`, `ручное значение` или `автоматически + утверждённая надбавка`. Возможность `автоматически` появляется только там, где источник подключён и проверен; ручное переопределение имеет причину, автора и срок действия. При возврате в автоматический режим администратор видит новое итоговое значение до подтверждения.

Публичный фронтенд обращается к нашему API: он отправляет параметры автомобиля и получает расчёт вместе с датой актуальности. Фоновые задания обновляют **справочные данные**, а не заранее считают все возможные комбинации машин. Это сохраняет ключи поставщиков на сервере, устраняет зависимость браузера от доступности внешнего API и позволяет воспроизвести цену.

До появления API Storybook использует локальный демонстрационный расчёт. В нём представлены все будущие группы расходов и редактируемые таблицы, но числа не публикуются на рабочем сайте и не считаются нормативным источником. При интеграции локальная функция удаляется, а UI сохраняет тот же структурированный запрос и построчный ответ.

Есть и другой тип интеграций: API ТКС или перевозчика может выдавать **индивидуальную смету для конкретного авто/маршрута**. Их разумно вызывать из нашего backend по запросу или из очереди для популярных карточек, затем кэшировать результат на согласованное время. Для таких запросов нужны таймаут, ограничение частоты и явное сообщение, если внешняя смета сейчас недоступна; прошлую цену нельзя молча выдавать за новую. Периодическая загрузка всех возможных комбинаций в БД бессмысленна. В админке нужно различать курс/тариф как справочник и полученное от поставщика коммерческое предложение для конкретного расчёта. Эти API не создают карточки автомобилей.

## Что проверить перед реализацией

- Получить от владельцев условия работы с брокером, банком и перевозчиками; уточнить фактические платежи и доступность расчётных API.
- Запросить документацию и тестовый доступ к API «Расчёт авто» ТКС; сравнить ответы с работой брокера и решить, является ли он расчётным поставщиком или лишь независимой проверкой наших правил.
- Собрать 15–20 реальных закрытых сделок по трём странам и сравнить все строки будущего расчёта с фактом. Отдельно проверить физлицо/юрлицо, возраст, объём, мощность, гибрид/электро и маршрут.
- Решить, какие цены показываются как ориентировочные и в какой момент менеджер утверждает окончательное предложение.
- Проверить по документам и с брокером текущие формулы пошлин, утильсбора, оформления и налогов. Исходный PHP-калькулятор использовать как перечень полей, не как нормативный источник.
