# Вход сотрудников и права доступа

Статус: проектное предложение на 22.09.2026, ожидает согласования с владельцем. Ожидается до 10 сотрудников; рабочая почта может быть не у каждого. Речь только об админке: клиентские личные кабинеты не планируются.

Для небольшой внутренней команды достаточно ASP.NET Core Identity внутри нашего backend и PostgreSQL. Отдельный сервер авторизации имеет смысл рассматривать при нескольких независимых продуктах или уже существующем корпоративном входе; сейчас он добавил бы обслуживание без ясной пользы.

## Рекомендуемый вход

- Учётная запись создаётся только по приглашению владельца/администратора; публичной регистрации сотрудников нет. У каждого свой аккаунт и назначенные роли, общего логина «менеджер» нет. Приглашение одноразовое и короткоживущее; первый телефон/адрес и личность сотрудника проверяются администратором вне самой ссылки.
- После активации сотрудник выбирает **любой доступный способ входа**: passkey **или** одноразовый код на заранее подтверждённый телефон либо email. Пароль помнить не нужно; passkey и код не обязаны использоваться вместе для обычного входа. Вход по коду не создаёт новый аккаунт и не даёт выбрать произвольный номер или адрес получателя.
- Passkey подтверждается Touch ID, Face ID, Windows Hello, PIN устройства или физическим ключом. Сервер хранит публичный ключ. [ASP.NET Core Identity в .NET 10 поддерживает WebAuthn/passkeys](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/passkeys/?view=aspnetcore-10.0); экран для Next.js придётся реализовать отдельно. Владельцу и администраторам желательно привязать два независимых устройства/ключа.
- Одноразовый код: короткий срок действия, однократное применение, ограничение запросов и попыток, без записи кода в журналы. Для короткого числового кода недостаточно одного быстрого хеша: требуется защищённое хранение с серверным секретом и строгий лимит попыток. [Рекомендации OWASP по OTP](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#one-time-password-otp-handling-and-storage).
- Если сотрудник потерял все способы входа, администратор после проверки личности отзывает прежние сессии и заново привязывает способ входа. Для владельца предусматриваем регламент восстановления с резервным администратором и ограниченными одноразовыми кодами восстановления.

Оба способа приводят к одной учётной записи, сессии и набору прав. Код из SMS или почты удобен, но слабее passkey: он зависит от безопасности телефонного номера/почтового ящика и может быть перехвачен фишингом. Для владельца и администраторов предлагаем обязать привязать passkey или TOTP, а критичные действия подтверждать им повторно. Встроенная реализация ASP.NET Core рассматривает passkey как самостоятельный способ входа, а не как готовый второй фактор для иных способов. [Ограничения реализации описаны Microsoft](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/passkeys/?view=aspnetcore-10.0#limitations).

## Телефон и Telegram

Телефон может быть идентификатором сотрудника и каналом для входа по коду, если он предварительно подтверждён. Смена номера требует отдельной проверки администратором, а не подтверждения только новым номером: SIM-карта может быть перевыпущена. [NIST относит телефонную сеть к ограниченным способам подтверждения](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#authentication-using-the-public-switched-telephone-network). Email-код тоже зависит от защиты почтового ящика; для почтового канала желательно требовать включённую двухфакторную защиту ящика.

Провайдер SMS пока не выбран. Для масштаба: [публичный тариф SMS.RU](https://sms.ru/price) указывает цену от 8,36–8,50 ₽ за сообщение в зависимости от оператора, а при использовании собственного буквенного имени отправителя — отдельные ежемесячные платежи операторам и за шаблоны. Точная стоимость кодов требует расчёта под номера команды и подходящий продукт провайдера. У [SMS.RU есть вариант кодов звонком без платы за буквенное имя](https://sms.ru/docs/api/api_group_call/code_call), но его удобство и надёжность надо проверить на реальных телефонах. Если нужны рабочие почтовые ящики, [стандартный тариф Timeweb сейчас указан как 120 ₽ в месяц за ящик](https://timeweb.cloud/solutions/mail); уже имеющиеся личные адреса не требуют покупки ящиков, но их защита и восстановление находятся вне контроля компании.

[Telegram поддерживает вход через OpenID Connect](https://core.telegram.org/bots/telegram-login), в том числе передачу подтверждённого номера с согласия пользователя. Он подтверждает владение Telegram-аккаунтом, но не даёт права работать в админке сам по себе: наш backend всё равно должен сопоставить его с заранее созданным и не заблокированным сотрудником. Рекомендация для первого запуска — **использовать Telegram только для уведомлений**, привязав его к аккаунту после основного входа. Уведомления содержат ссылку и минимум сведений о клиенте. Вход через Telegram можно добавить позже, если команда действительно предпочитает его и согласованы зависимость от сервиса и восстановление доступа.

## Сессии и защита действий

- Авторизацию проверяет .NET API на каждом защищённом запросе; Next.js скрывает недоступные экраны для удобства, но не заменяет серверную проверку прав.
- Для браузера используем cookie `HttpOnly`, `Secure`, `SameSite`; не храним токен доступа в `localStorage`. [Microsoft рекомендует cookies для браузерных приложений](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0#use-token-based-authentication). Админка и её API должны работать на одном origin через reverse proxy. Для изменяющих запросов также нужна защита от CSRF.
- Сессии видны в профиле: сотрудник может выйти с текущего или всех устройств; администратор может немедленно заблокировать аккаунт и отозвать доступ. Для немедленного отзыва сервер хранит запись каждой активной сессии и проверяет её на защищённых запросах; одного долгоживущего cookie без серверной проверки недостаточно. Ограничение попыток входа и журнал событий обязательны.
- Изменение правил цен, общего коэффициента, ролей, экспорт заявок и привязка нового способа входа требуют свежего подтверждения через passkey или TOTP, а не повторного ввода кода в тот же телефон или ящик. Для этих действий фиксируем автора, время и результат.
- Права строятся по операциям: менеджер ведёт заявки и свои автомобили; редактор публикует материалы; ответственный за цены меняет тарифы; владелец управляет пользователями и интеграциями. Роли можно совмещать, но доступ к заявкам и персональным данным выдаётся по необходимости.

## Что нужно решить до реализации

1. Будет ли отдельный постоянный адрес админки, например `admin.perviyzakaz.ru`: passkeys привязаны к домену, его лучше выбрать заранее. Тестовое окружение имеет собственные ключи входа.
2. Какие телефоны и почтовые адреса будут закреплены за каждым из не более чем 10 сотрудников; какие у них устройства/браузеры. Выбрать канал для каждого сотрудника и оценить долю SMS-входов.
3. Кто второй администратор на случай недоступности владельца, как хранятся резервные ключи и как подтверждается восстановление аккаунта.
4. Проверить тарифы и доставку SMS/звонков на конкретные операторы команды. Уточнить, нужны ли менеджерам уведомления в Telegram и какие данные допустимо отправлять туда с учётом обработки персональных данных.
