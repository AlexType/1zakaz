# Вход сотрудников и права доступа

Статус: рекомендация на 22.09.2026, ожидает согласования с владельцем и проверки устройств команды. Речь только об админке: клиентские личные кабинеты не планируются.

Для небольшой внутренней команды достаточно ASP.NET Core Identity внутри нашего backend и PostgreSQL. Отдельный сервер авторизации имеет смысл рассматривать при нескольких независимых продуктах или уже существующем корпоративном входе; сейчас он добавил бы обслуживание без ясной пользы.

## Рекомендуемый вход

- Учётная запись создаётся только по приглашению владельца/администратора; публичной регистрации сотрудников нет. У каждого свой аккаунт и назначенные роли, общего логина «менеджер» нет. Приглашение одноразовое и короткоживущее; для первого входа администратор подтверждает личность сотрудника и передаёт отдельный код по другому каналу.
- Основной способ — **passkey**: вход подтверждается Touch ID, Face ID, Windows Hello, PIN устройства или физическим ключом. Для пользователя это одно действие, а сервер хранит публичный ключ, не пароль устройства. [ASP.NET Core Identity в .NET 10 поддерживает WebAuthn/passkeys](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/passkeys/?view=aspnetcore-10.0), но готовый интерфейс есть только в шаблоне Blazor: для Next.js понадобится собственный экран регистрации и входа по документированному протоколу.
- При создании аккаунта сотрудник привязывает passkey; владельцу и администраторам желательно иметь второй независимый ключ или устройство. Запасной путь для сотрудников — индивидуальный пароль **вместе** с кодом TOTP из приложения-аутентификатора. Для владельца отдельно готовим ограниченные одноразовые коды восстановления и регламент хранения. [TOTP поддерживается ASP.NET Core Identity](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/mfa?view=aspnetcore-10.0).
- Если сотрудник потерял все способы входа, администратор после проверки личности блокирует прежние сессии и выдаёт новое одноразовое приглашение. Восстановление только по SMS, Telegram-сообщению или ссылке из почты не открывает админку автоматически.

Passkey не освобождает от настройки резервного доступа и защиты учётной записи. Встроенная реализация ASP.NET Core рассматривает passkey как **основной способ входа**, а не как встроенный второй фактор; особенно чувствительные операции проверяем отдельной повторной аутентификацией и правами. [Ограничения реализации описаны Microsoft](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/passkeys/?view=aspnetcore-10.0#limitations).

## Телефон и Telegram

Телефон хранится как контакт сотрудника и, при необходимости, проверяется, но **SMS-код не является единственным способом входа**: номер может сменить владельца или SIM-карта может быть перевыпущена. [NIST относит SMS/телефонную сеть к ограниченным способам подтверждения](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#authentication-using-the-public-switched-telephone-network).

[Telegram поддерживает вход через OpenID Connect](https://core.telegram.org/bots/telegram-login), в том числе передачу подтверждённого номера с согласия пользователя. Он подтверждает владение Telegram-аккаунтом, но не даёт права работать в админке сам по себе: наш backend всё равно должен сопоставить его с заранее созданным и не заблокированным сотрудником. Рекомендация для первого запуска — **использовать Telegram только для уведомлений**, привязав его к аккаунту после основного входа. Уведомления содержат ссылку и минимум сведений о клиенте. Вход через Telegram можно добавить позже, если команда действительно предпочитает его и согласованы зависимость от сервиса и восстановление доступа.

## Сессии и защита действий

- Авторизацию проверяет .NET API на каждом защищённом запросе; Next.js скрывает недоступные экраны для удобства, но не заменяет серверную проверку прав.
- Для браузера используем cookie `HttpOnly`, `Secure`, `SameSite`; не храним токен доступа в `localStorage`. [Microsoft рекомендует cookies для браузерных приложений](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0#use-token-based-authentication). Админка и её API должны работать на одном origin через reverse proxy. Для изменяющих запросов также нужна защита от CSRF.
- Сессии видны в профиле: сотрудник может выйти с текущего или всех устройств; администратор может немедленно заблокировать аккаунт и отозвать доступ. Для немедленного отзыва сервер хранит запись каждой активной сессии и проверяет её на защищённых запросах; одного долгоживущего cookie без серверной проверки недостаточно. Ограничение попыток входа и журнал событий обязательны.
- Изменение правил цен, общего коэффициента, ролей, экспорт заявок и привязка нового способа входа требуют свежего подтверждения личности. Для этих действий фиксируем автора, время и результат.
- Права строятся по операциям: менеджер ведёт заявки и свои автомобили; редактор публикует материалы; ответственный за цены меняет тарифы; владелец управляет пользователями и интеграциями. Роли можно совмещать, но доступ к заявкам и персональным данным выдаётся по необходимости.

## Что нужно решить до реализации

1. Будет ли отдельный постоянный адрес админки, например `admin.perviyzakaz.ru`: passkeys привязаны к домену, его лучше выбрать заранее. Тестовое окружение имеет собственные ключи входа.
2. Сколько сотрудников и какие у них устройства/браузеры; есть ли корпоративная почта для приглашений. Почта — канал приглашения, а не единственный фактор входа.
3. Кто второй администратор на случай недоступности владельца, как хранятся резервные ключи и как подтверждается восстановление аккаунта.
4. Нужны ли менеджерам уведомления в Telegram и какие данные допустимо отправлять туда с учётом обработки персональных данных.
